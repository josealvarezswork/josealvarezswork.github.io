Same Page — a consistency auditor for my own case studies

I built a process that checks my design work against itself. It quotes the exact sentence, shows where two pages disagree, and a small script checks that every quote really is on the page.

Own tool · one user so far Role: process design, validation rules, auditing Built as a Claude skill with a Node validator Status: in use on this portfolio, not tested with other designers
The problem

My own pages disagreed with each other

I had two case studies and two design-system pages. Read one by one, they looked fine. Read side by side they were not: a state count that differed between two pages, XP values that did not match, and a test that appeared with results when it had only been planned.

A reviewer will read them side by side. So the question became: can a process do that reading for me, before anyone else does?

What it is

Two modes, one rule: quote it or it does not count

Mode A — audit pages I already published

It reads the pages, finds contradictions and unsupported claims, and writes each finding with the exact quote. A validator then checks every quote against the page text. If the quote is not there, the audit fails.

The findings become a fix list ranked A, B and C. I make the edits. Then it runs again in a fresh context and reports what was fixed, what is still open and what is new.

Mode B — work up a project in stages

Eight stages, each writing one file: brief, strategy, research, journey, synthesis, audit, design system and a case-study skeleton.

The last stage does not write the case study. It leaves marked holes for the decisions that are mine, and the final check fails while any hole is open.

A skill is a packaged set of instructions Claude loads for a task. The validator is a small Node script that reads my pages and checks the audit against them. Stages 1 to 8 belong to Mode B; stage 9 is Mode A.

What failed

My first approach lost to a plain prompt

My first approach had the tool write whole case studies from an idea. I tested that blind: a fully generated case study for a new idea against one written from a plain prompt. The generated one lost on every criterion: voice, how visible the decisions were, and how useful it would be in an interview. The judge called it AI-looking.

That is one run, one judge and the same model family, so it is a signal and not a verdict. It was enough to stop me from presenting generated work as mine.

What I changed

From writing the case study to checking it

The tool stopped writing the case study

Stages 1 to 6 became a consistency audit. Stage 8 became a skeleton with holes. The decisions stay with the designer.

The validator got strict

I seeded known faults into test projects to see what it caught. The first version caught 8 of 53 seeded faults. After I rewrote it to enforce the schema, it caught all 37 in a later set. The two sets were different sizes, so this is not a like-for-like comparison.

A new provenance rule: any color, name or percentage in an output must trace back to something I declared.

What it found on my own pages

Real findings, and what I did about them

I ran it on the Cuak and DuoGit pages. These three examples are all from Cuak, each with what I decided.

One finding, end to end

The pages said: the case study said “map user behavior to one of five emotional states”, and its design-system page said “4 emotional states, 1 behavioral arc”.

The audit wrote: a contradiction, five against four, with both quotes.

The script checked: that both quotes were on the pages. They were, so the finding stood. After I fixed the page, the same audit fails that check, because the second quote no longer exists. That is intended: an old audit cannot pass against a page that has changed.

A test shown as done

The page reported test results and a tester quote. The test was only planned.

I removed the results and the quote from six files (the case study, resume, methodology page, project data, home page and about page) and relabeled the section as a testing plan.

An integration shown as built

A bank-data integration was described as part of the product. It was a design only, because bank sandboxes are hard to get access to.

The pages now say designed, not connected, and name the next step.

Two pages, two counts

The case study and its design-system page did not agree on how many emotional states exist.

I aligned both pages on five states plus a recovery moment.

Each re-audit also turned up new findings, some caused by my own fixes. For example, I invented two card names while aligning the states, and the next audit flagged one of them as contradicting the page. That is part of the loop, not a failure of it.

What is not proven

What I do not know yet

  • It has one user, me, on my own pages.
  • I have not published the test case, the judge's criteria or the seeded faults, so these numbers cannot be reproduced yet.
  • The blind test was one run, one judge, one model family.
  • I have not tested whether stages 1 to 7 earn their place, or whether a plain prompt would do as well.
  • I have not measured the cost of a run against that plain prompt.
  • I do not know whether fixing the findings changes how a reader sees the pages.
  • The case-study skeleton has not been generated from scratch, only on projects I had already worked on.
What is next

The next stage I want is accessibility. Color contrast is a calculation, not an opinion, so it fits the rule this process already follows: a finding has to match something that can be checked. The first target is my own portfolio. I will only add it to this page once it runs.
