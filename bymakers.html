01 — Problema

Tener un sitio web cuesta. No tenerlo también.

Para un emprendedor pequeño, pagar el desarrollo de un sitio web es inaccesible. La alternativa es improvisar: álbumes de WhatsApp, PDFs que nadie actualiza, listas de precios por correo. Cada vez que hay un producto nuevo o un precio cambia, hay que reenviar todo de nuevo. El cliente recibe un PDF desactualizado o un link roto — y la venta se pierde.

El problema no es falta de esfuerzo. Es que las herramientas disponibles están diseñadas para empresas con presupuesto y equipo técnico. Un emprendedor solo necesita mostrar sus productos de forma profesional y recibir pedidos — sin pagar por un sitio ni depender de un developer.

● El problema

Sin catálogo digital propio, los emprendedores improvisan con WhatsApp, PDFs y hojas de cálculo. Cada cambio de precio o producto nuevo implica actualizar y reenviar manualmente a cada cliente.

● El costo real

No es solo imagen. Es tiempo y ventas perdidas. Un PDF desactualizado genera desconfianza. Un link roto cierra la conversación. Depender de WhatsApp para mostrar el catálogo escala muy mal cuando el negocio crece.

Un emprendedor que no puede mostrar sus productos de forma profesional compite con una mano atada.

"Necesito algo donde mis clientes puedan ver todo con precios y me escriban directo — sin que yo tenga que mandar fotos cada vez."

— Primera cliente · emprendedora en Colombia
02 — Investigación

El problema no era tecnológico — era de acceso y confianza.

La hipótesis inicial era que los emprendedores necesitaban un e-commerce. La investigación — conversaciones con la primera clienta y observación de cómo operan los pequeños negocios en Colombia — reveló algo distinto: no quieren e-commerce. Quieren seguir cerrando ventas por WhatsApp porque es su canal de confianza. Lo que necesitan es una capa de presentación profesional que se pueda compartir como link y que alimente su flujo existente de conversación.

No es una startup tech. Es alguien con productos, un celular y sin presupuesto para un sitio web.

El producto tiene dos usuarios: el emprendedor (admin) y su cliente (catálogo público). El case study se enfoca en el emprendedor porque es el usuario que paga — y el que tiene las limitaciones técnicas y económicas más fuertes. El perfil aplica a cualquier rubro: moda, artesanías, repuestos, comida, electrónica, lo que sea.

04 — El trade-off

E-commerce completo vs. catálogo con cierre por WhatsApp

Construir un e-commerce completo (carrito, pasarela de pago, envíos) habría sido la solución "completa" pero completamente equivocada para el usuario. Los emprendedores pequeños cierran ventas a través de conversación directa — no quieren reemplazar eso, quieren llegar a esa conversación mejor preparados. La decisión de producto: catálogo profesional + puente a WhatsApp, no una tienda.

WhatsApp no es el problema — es el canal de confianza. El producto no lo reemplaza, lo potencia.

06 — Decisiones técnicas

Multi-tenancy real, no simulada

Cada decisión técnica responde a una restricción del usuario real. Row Level Security en Supabase para aislamiento total entre tenants. Imágenes optimizadas a WebP porque las comerciantes y clientas están en planes de datos limitados. Server components para que los catálogos públicos indexen en Google.

🖼

Pipeline de imágenes

Upload → Crop → 3× WebP

Thumbnail, card y large — optimizadas para planes de datos limitados en LATAM.

🔒

Aislamiento por tenant

Tenant A → RLS → Solo sus datos
Tenant B → RLS → Solo sus datos

Row Level Security en Supabase. No hay forma de acceder a datos de otro tenant.

07 — Principios de diseño

Tres principios detrás de cada decisión

📱

Mobile-first, siempre

El 90% de las usuarias administran desde el celular. Cada pantalla se diseñó primero en 375px. Si no funciona en móvil, no existe.

💬

WhatsApp es el checkout

No competir con el canal de confianza. Potenciarlo. El producto termina donde WhatsApp empieza.

🎨

Profesional sin presupuesto

Restricciones inteligentes: paletas curadas, tipografías probadas, layouts fijos. El catálogo se ve bien aunque el emprendedor no sepa de diseño ni tenga equipo.

09 — Retrospectiva

Lo que construir un SaaS real me enseñó

✅ Lo que funcionó

Construir multi-tenant desde el día uno fue la decisión correcta. RLS forzó un modelado de datos limpio desde el principio.

La decisión de WhatsApp como checkout se validó inmediatamente: la primera clienta nunca pidió integración de pagos. El canal humano era suficiente y preferido.

🔍 Lo que haría diferente

Invertir antes en el flujo de onboarding. La primera clienta necesitó setup guiado — el producto asumía que la usuaria sabría navegarlo sola.

Analytics desde el día uno. Sin datos de uso, las decisiones de producto se basan en conversación en vez de evidencia. Agregaría tracking de eventos y métricas de conversión desde el primer deploy.
